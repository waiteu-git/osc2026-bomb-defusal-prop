## 1. 経緯・前提

- 2026-09-16(ユーザー決定): 6本(実物どおり)、★は固定印刷ではなく電子制御(単純LED方式)。
- 2026-09-24(機能会議・ハブ連絡): ワイヤー系モジュールは「実際にワイヤーを切る/端子台で交換/各ワイヤーと基板の接続部にNeoPixel」。通信はI2C共有バスから区画ごとのUART専用線へ。パネルは80mm角で進行。四隅約15mm角(穴径10mm、中心位置未確認)には部品を置かない。
- 2026-09-24(ワイヤー担当セッションでユーザー決定): 端子台=秋月WJ141V-2.54-02P-146-00A、NeoPixel=WS2812B(V5)、3.3V直結。本モジュールもこれに合わせる。
- 2026-09-27(ユーザー決定、ハブ経由): 「ワイヤー」と「複雑ワイヤ」はハードウェアをこの基板1本に統合する。
- 2026-09-27(ユーザー指示): NeoPixelをWS2812B(V5)から**SK6812MINI-E(秋月g115478)**に変更。
- 2026-09-27(ユーザー指示): 端子台を「2極端子台5個/片側、中央(ワイヤー3・4)だけ2極とも配線」に確定(§6)。単独グループの回路図シンボルもConn_01x02に統一(ユーザー指摘「1極品は無いから全部2極端子台にして」)。
- 2026-09-27(ユーザー指示、のち撤回): 「端子台につながる分は全部見れるように」を、GPIO検知回路(EXTRA1-4)+専用の接続状態インジケータLED10個という形で実装したが、**ユーザーから「そんなものをつけろとは言っていない」と明確に否定され、撤回**。
- **2026-09-28(ユーザー指示、確定)**: 実際の意図は「各ワイヤーが挿さる場所(端子)にNeoPixelを置き、その光り方で複雑ワイヤの属性(色・★・LED点灯)を再現する」ことで、GPIO検知や専用ステータスLEDではなかった。「端子につながる分を全部見れるように」は「端子台が物理的に持つスロット数(信号側・GND側とも10極ずつ)全部にNeoPixelを置く」という意味だった。スタート(信号側端子)とゴール(GND側端子)それぞれに1個ずつ必要、との追加説明を受け、**信号側10極+GND側10極=NeoPixel20個**の設計に確定。EXTRA1-4検知回路・接続状態インジケータLED10個は撤去。
- **2026-09-28(ユーザー指摘、重要)**: 「回路図をこっちで位置を変えたり消したりしているのは意味のある行為であって変えてほしくない」との指摘を受け、以降は生成スクリプトによる全体再生成をやめ、対象を限定した外科的編集(`_sch_surgery.py`)に切り替えた。

## 2. モジュール概要(公式マニュアル13ページ / KTANE Wiki / 攻略ブログPart2)

- ワイヤー最大6本。各ワイヤーに「上のLED」「下の★マーク用スペース」があり、ワイヤーは縞模様(複数色)もあり得る。
- 各ワイヤーの属性は独立な4つ: **赤を含むか / 青を含むか / ★があるか / LEDが点灯か**。判定は5記号のベン図(C=切る、D=切らない、S=シリアル末尾が偶数なら切る、P=パラレルポートありなら切る、B=電池2本以上なら切る)。
- 共有パラメータ(ホストが通信の都度UARTでモジュールへ書き込む1バイト。ゲーム中の値は不変): bit0=シリアル末尾が奇数なら1(偶数判定はbit0==0)、bit2=電池2本以上、bit4=パラレルポートあり。複雑ワイヤが使うのはこの3ビットのみ。ハードウェア(GPIO)への影響なし、ファームウェア側の対応事項。
- ベン図の正確な判定表(16通り)はソフト担当がマニュアルの図から実装する(ハブに画像あり)。本メモでは扱わない。

## 3. 表示方式の検討経緯

### 3-1. 最終方式(2026-09-28確定): 端子ごとNeoPixel、20個

複雑ワイヤの属性(色・★・LED点灯)は、**各ワイヤーが実際に挿さる場所(端子)そのもの**にNeoPixelを置き、その光り方(色・点滅パターンなど)で再現する。ワイヤーは信号側端子(スタート)とGND側端子(ゴール)の間を渡す物理部品なので、その両端それぞれにNeoPixelが要る。

端子台はWJ141V(2極品)を使うため、5個/片側×2極=**信号側10極・GND側10極、計20極**が物理的に存在する(うち実際にワイヤーが挿さるのは6極ずつ、残り4極ずつは端子台が2極品しかないために生まれる予備)。ユーザー指示「端子台につながる分は全部見れるように」は、この20極すべてにNeoPixelを置くという意味だった。

- **NeoPixel20個を1本のデータ線にデイジーチェーン**(GP8、直列330Ω)。
- チェーン順: **index 0-9(D1-D10)=信号側10極(スタート)**、**index 10-19(D11-D20)=GND側10極(ゴール)**。各々の並び順はTERMINAL_GROUPS(S1,S2,S34,S5,S6の順、各端子台の1極目→2極目)と同じ。
- 電気的には、NeoPixelは各端子の信号ネット(WIREn_T/GND)とは無関係(色データのGPIOチェーンのみ)。「どのNeoPixelがどの物理位置か」はDescriptionプロパティと`gen_complicated_wires_sch.py`のSIGNAL_POLES/GND_POLESに明記。
- 色・★・LED点灯という3つの独立属性を1個のNeoPixel(RGB+点滅制御)でどう表現するかは、**ソフト担当の符号化次第**(ハードは「各端子にNeoPixelが1個ある」ことしか保証しない)。実際に使われない予備極(4極×2側)は常時消灯でよい。

### 3-2. 物理ワイヤーの色は不要(論理色をNeoPixelが決める)
GPIOでは被覆の色を検知できないので、ワイヤー自体はどの色でもよい(Wire Sequenceと同じ結論)。ラウンド開始時にファームが各位置の色をランダムに決めてNeoPixelに表示する。

### 3-3. 検討の変遷

1. (2026-09-16〜27前半)色=NeoPixel、LED点灯=単純LED、★=単純LED(裏面バックライト)の3素子独立案。
2. (2026-09-27)★・LED点灯もNeoPixel化。色・LED点灯・★がそれぞれ別のNeoPixel(18個)。
3. (2026-09-27)色とLED点灯を1個のNeoPixel(上部)に統合、★は別(下部)。18個→12個。パネル端の2バンド(上部×6、★×6)方式。
4. (2026-09-27→撤回)「端子につながる分を全部見れるように」を、GPIO検知(EXTRA1-4)+専用インジケータLED10個と誤解して実装 → ユーザーに明確に否定された。
5. **(2026-09-28最終)** 上部/★のバンド方式そのものをやめ、**各端子(スタート/ゴール)にNeoPixelを直接置く**方式に変更。信号側10極+GND側10極=20個。

### 3-4. ★の表示方法
星型のステンシル窓や裏面バックライトは使わず、NeoPixelの点灯色/点滅パターンで★の有無を表現する(ファーム側の実装判断)。

### 3-5. 動作モード:「ワイヤー」/「複雑ワイヤ」共用ハードウェアについて
2026-09-24に「共通基板案」が一度検討されたが、NeoPixelのチェーン構成・個数が今回の変更(端子ごと20個)で大きく変わったため、**共用ハードウェアの前提(チェーンindexの一部を消灯するだけで両モードに対応)は再検討が必要**。ソフト担当・ハブとのすり合わせ待ち(§8)。

### 5-2. ブロック図

```
 JST XH 4P (J1)
  Pin1 ------------------------ GP0 (UART0 TX)
  Pin2 ------------------------ GP1 (UART0 RX)
  Pin3 (5V) -+-----------------+---- Pico 2 VSYS(pin39)
             |                 +---- NeoPixel VDD(チェーン) --[C1 100uF, C2 0.1uF]-- GND
  Pin4 (GND) --- 共通GND

 端子台(信号側、5個/片側): S1(W1) S2(W2) S34(W3,W4) S5(W5) S6(W6)  [WJ141V、S34だけ2極とも配線]
 端子台(GND側、5個/片側):  G1(W1) G2(W2) G34(W3,W4) G5(W5) G6(W6)
   ワイヤーn: 対応する信号極 ==ワイヤー== 対応するGND極

   信号極 --[1k]--+-- GPn (n=2..7)
                  |
                 [10k]
                  |
                 +3V3            (ワイヤー接続中: GPnは約0.3V=LOW / 切断: 3.3V=HIGH)

 GP8 --[330]--> D1(S1極1/スタート)→D2(S1極2/予備)→D3(S2極1)→...→D10(S6極2/予備)
                →D11(G1極1/ゴール)→...→D20(G6極2/予備、DOUT未接続)
 GP9 --[47]--> 状態LED(緑) --> GND
```

### 5-3. 各回路の根拠
- **断線検出**: 信号側端子とGND側端子の間をワイヤーが渡す。ワイヤーあり→端子がGNDに落ちる→ピン電圧=3.3V×1k/(10k+1k)=0.3V(RP2350のVIL上限0.8Vより十分低い)。切断→10kでHIGH。外付け10kはばらつき吸収、直列1kΩはESD対策。内蔵プルアップは無効(外付けを使う)。ソフトのデバウンス数十〜100ms。
- **端子台の共有(S34/G34)**: ワイヤー3・4だけ、1個のWJ141V(2極)の両方の極を使う。極1→ワイヤー3、極2→ワイヤー4で、電気的には他のワイヤーと同じ扱い(それぞれ別ネット`WIRE3_T`/`WIRE4_T`に接続。短絡しない)。
- **端子ごとNeoPixel(20個、2026-09-28確定)**: 信号側・GND側それぞれの全10極にNeoPixelを1個ずつ置き、複雑ワイヤの属性表示に使う。電気的には端子のネットと無関係(色データのGPIOチェーンのみ)。実際に使われない予備極(4極×2側)は常時消灯でよい。
- **NeoPixel電源**: VDD=JST Pin3の5V。DINはPico 2の3.3V直結、DIN直前に330Ω直列(1個目のみ)。20個目(D20)のDOUTは未接続。100µF電解は電源の安定化。
- **状態LED**: keypad等と同じ仕様(GPIO+47Ω、解除済みで点灯)。単純LEDのまま。
- **電源**: JST Pin3(5V、ホスト側で区画ごとにポリスイッチ、ホールド約200mA)→Pico 2のVSYS。3.3VはPico内蔵レギュレータ。
- **UART**: J1のPin1/2を直結。プルアップは付けない。

### 5-4. 電流見積り(200mA予算)——⚠️要ユーザー判断

20個すべてがNeoPixelなので、**電流のハード的な歯止めがない**(ソフトウェアの輝度指定だけが上限を決める)。ただし実際のゲームでは20個中12個(実在する6本のスタート側+ゴール側)しか光らない想定で、残り8個(予備極)は常時消灯のはず。

| ケース | 計算 | 電流 |
|---|---:|---:|
| 待機(全消灯、静止電流1mA/個×20) | - | 20mA |
| **絶対最悪ケース(輝度上限なし=255、20個フル白色)** | 3ch×12mA×20個 | **720mA** |
| **実運用最悪ケース(輝度上限なし、実在12個のみ点灯、予備8個は消灯)** | 3ch×12mA×12個 | 432mA(旧12個版と同じ) |
| Pico 2(推定)+状態LED(47Ω) | - | 約36mA |
| **絶対最悪ケースの合計** | | **約756mA(予算の3.8倍)** |
| **実運用最悪ケースの合計** | | 約468mA(予算の2.3倍) |
| MAX_BRIGHTNESS=20、実運用12個フル白色 | 432×20/255 | 約33.9mA |
| MAX_BRIGHTNESS=20時の合計(実運用) | | **約71.7mA(予算の36%)** |
| MAX_BRIGHTNESS=20、予備8個も誤って全点灯した場合 | 720×20/255 | 約56.5mA |
| MAX_BRIGHTNESS=20時の合計(絶対最悪) | | 約92.5mA(予算の46%) |

**結論**: MAX_BRIGHTNESS=20〜30程度に制限すれば200mA予算に十分収まるが、**この値はソフトウェアが必ず適用しないと危険**(ハブの既存ルール「WS2812Bを使うモジュールは輝度キャップを入れてから最初の通電をする」)。**予備極(8個)を誤って点灯させないこと自体もファーム側の安全対策として重要**(意図的にOFFのまま管理する)。ブリングアップ時に実測必須。

## 6. 80mm角の配置案

前提: パネル80×80mm、四隅15×15mmは部品禁止(穴径10mm、中心位置未確認)。ワイヤーは実物どおり縦、ピッチ8mm。

**端子台の構成(2026-09-27確定、変更なし)**: 信号側・GND側とも5個ずつ。TERMINAL_GROUPS = `[(1,), (2,), (3,4), (5,), (6,)]` — ワイヤー1,2,5,6は専用の端子台(2極品の1極のみ配線)、ワイヤー3・4だけ中央の1個の端子台(2極とも配線)を共有。

寸法根拠: 端子台WJ141V 7.62×12.9mm(1極でも2極配線でも筐体寸法は同じ)。

**⚠️2026-09-28: NeoPixel20個(端子ごと)の物理配置は未検証**。`complicated_wires_layout80_check.py`のモデルは旧方式(上部NeoPixel×6・★NeoPixel×6をパネル上下端に配置)のまま部分的に残っている(端子台・可視ワイヤーのジオメトリ自体は影響を受けないため有効)が、「各端子のすぐそばにNeoPixelを1個ずつ、信号側10個・GND側10個」という新方式の物理レイアウトはまだモデル化・検証していない。端子台自体が既にタイト(隙間0.38mmが2箇所)なため、そのすぐ隣にNeoPixel(占有4×4mm程度)を追加で置けるかは要検討(§8)。

チェック結果(旧モデルの端子台・可視ワイヤー部分、`python complicated_wires_layout80_check.py`): 四隅15mm角への侵入なし、パネル縁から最小3.0mm、部品同士・ワイヤー経路との重なりなし。**端子台どうしの隙間(信号側・GND側とも同じ)は [0.38, 4.38, 4.38, 0.38] mm**(S1-S2間とS5-S6間が0.38mm、S2-S34間とS34-S5間は4.38mm)。

### ⚠️端子台の隙間0.38mm(2箇所)について(未解決、ユーザー判断待ち)
5個中2箇所(両端寄りのS1-S2間、S5-S6間)は、隣り合う端子台(WJ141V本体7.62mm幅)どうしの隙間が0.38mmしかない。中央2箇所(S2-S34間、S34-S5間)は約4.4mmに改善している。
- **WJ141Vの1極品(WJ141V-2.54-01P)は秋月電子で販売されていないことを確認済み**。
- ピッチを8mmから広げても大きくは改善しない: 四隅の15mm角キープアウトにより、ピッチの上限は約8.45mm。
- **ユーザー判断が必要**: 残る2箇所の0.38mmの隙間を、実物WJ141Vどうしを並べて許容できるか(押しボタン/レバー部分が隣に干渉しないか)は、資料だけでは分からない。不合格ならねじ式g114217への変更を検討。

### 成立性の所見と代替
- 端子台・可視ワイヤーの配置(6本分)は収まる。本数の削減は不要。
- 縦挿しの端子台は高さ13.8mm。ワイヤーは端子台の上面から出て、その高さで基板と平行に渡す形になる。実機の見た目は要確認。
- 基板の裏側(Pico 2・JST・抵抗)の配置は、基板製法(ユニバーサル/発注PCB)とJST取り出し辺の決定待ち。
- **NeoPixel20個(端子ごと)の具体的な物理位置・実装可否は未検証**(§8)。

## 7. KiCad回路図と動作確認

### 7-1. KiCad回路図(作成・検証済み)
ファイル: `complicated_wires.kicad_sch` / `.kicad_pro` / `.kicad_prl`(A3)。

**2026-09-28: ワークフロー変更**。`gen_complicated_wires_sch.py`は今後、`.kicad_sch`を直接上書き生成する用途では使わない(ユーザーがGUIで手動配置した内容を壊すため)。代わりに:
1. 生成スクリプトを編集し、**別ファイル(スクラッチ)に出力**してERC・ネットリストで論理トポロジーを検証する。
2. 検証済みのロジックを、`_sch_surgery.py`(パーサ・ピン座標計算ヘルパー)を使って、実際の`.kicad_sch`に対する**対象限定の外科的編集**(該当シンボル・ワイヤー・ラベルの削除/追加のみ)として反映する。ユーザーが手動配置した既存要素(端子台の位置など)は一切変更しない。
3. 反映後、実ファイルに対して改めてERC・ネットリスト検証を行う。

- モデル化: 端子台は`add_terminal_row()`ヘルパーで生成(変更なし)。NeoPixel(D1〜D20)は**SK6812MINI-E**。**チェーン順: D1〜D10=信号側端子台10極(スタート、SIGNAL_POLES順)、D11〜D20=GND側端子台10極(ゴール、GND_POLES順)**。各NeoPixelのDescriptionプロパティに「どの端子台Ref・pole・ワイヤー番号(または予備)」かを明記。D20のDOUTはno_connect。状態LED(LED1)は単純LEDのまま、GP9(47Ω経由)。
- **ERC**(`kicad-cli sch erc`): **0件**(2026-09-28、端子ごとNeoPixel20個化後に再検証)。
- **ネットリスト**(`kicad-cli sch export netlist`)を、スクラッチ生成時の期待ネット(40ネット)とメンバー集合で照合: **不一致0**(KiCadが未ラベルの直結ネットを自動命名した分の名前差のみ、接続関係は完全一致)。`WIRE3_T`はS34.1のみ、`WIRE4_T`はS34.2のみに接続(共有していても別ネットのまま)を確認。
- 座標は全て1.27mm格子。
- **既存の手動配置(GND側端子台をS側の右隣、x=43付近に移動済みなど)は今回の編集で一切変更していないことを確認済み**。

### 7-2. 動作確認スクリプトと実行手順
スクリプト: `complicated_wires_bringup_test.py`(MicroPython、Thonnyで実行)。配線確認のみが目的で、ベン図の判定・ラウンド生成はソフト担当が実装する。

**準備(ブレッドボード、回路図と同じ配線)**
| 部品 | 接続 |
|---|---|
| ワイヤー1〜6(擬似) | 各ワイヤーは「GPIO(GP2〜GP7)→1kΩ→端子行」と「GPIO→10kΩ→3V3(pin36)」、端子行とGNDの間にジャンパー線(=ワイヤー。抜けば切断) |
| NeoPixel×20(SK6812MINI-Eまたは手持ちのWS2812B系、1本のチェーン) | VDD=5V(USBのVBUS pin40)、GND、DIN←GP8(330Ω経由)、各DOUT→次のDIN |
| 状態LED(緑) | GP9 → 47Ω → LED → GND |

**手順と期待される結果**
1. Thonnyでスクリプトを開いて実行(F5)。起動直後、状態LEDが0.15秒間隔で3回点滅する(生存確認)。
2. NeoPixelが1個ずつ、白→赤→青→緑の順に、index 0→19の順で光る。順番が違えばチェーンの接続順を確認する。
3. スタート側(実在6箇所)・ゴール側(実在6箇所)のインジケータが順に点灯する(配線・チェーン順の確認用、仮の色)。
4. REPLに各ワイヤーの状態が一覧表示される。監視ループで、ジャンパーを抜くと該当ワイヤーのスタート側・ゴール側の両方のNeoPixelが緑→赤に変わる。全ワイヤー接続中だけ状態LEDが点灯する。
5. 実測項目(§5-4・§8): (a)USB電流計でアイドルと全点灯時の電流(輝度上限の値ごとに必ず実測)、(b)ワイヤー接続中のGPIO電圧(約0.3V)、(c)NeoPixelのDIN電圧とVDDの実電圧。
6. NeoPixelがちらつく・点灯しない場合は、DINのVIHマージン不足が濃厚。ダイオード降圧(VDD約4.3V)またはレベルシフタ(SN74AHCT125N)を検討する。

## 8. 未決定・リスク・ユーザー確認事項

1. **(要ユーザー判断)各NeoPixelでの色+★+LED点灯の符号化方式**(§3-1): ハードは各端子に1個のNeoPixelを用意しただけで、3つの独立属性をどう表現するかはソフト担当の実装次第。ハブ経由ですり合わせが必要。

4. **(要ユーザー判断)20個NeoPixelの輝度上限値**(§5-4): MAX_BRIGHTNESSの具体的な値をソフト担当と確定し、必ず最初の通電前にファームへ実装する。**予備極8個を誤って点灯させない実装**も安全上重要。
5. **端子台の外し方・保持力・挿抜耐久**: 全て資料に記載なし。実物サンプルの購入・実測はまだ未着手。
6. **NeoPixelのVIHマージン**: SK6812MINI-EはVIH=0.7×VDD=3.5V(@VDD=5V)で、3.3V直結は規格上0.2V不足。実測で問題なければそのままでよいが、不合格ならダイオード降圧またはレベルシフタが必要。
7. **SMD(SK6812MINI-E、3.2×2.8mm)の手はんだ**: 20個(旧12個から増加)。footprint名"ReverseMount"とデータシートの"Top SMD"表記の整合は現物入手時に要確認。
8. 断線検出の抵抗値(1k/10k)の実測妥当性。
9. パネル・ねじ穴中心・JST取り出し辺・基板製法は未定。
10. **「ワイヤー」/「複雑ワイヤ」共用基板案**(§3-5): 端子ごとNeoPixel20個化により、共用の前提(チェーンの一部を消灯するだけ)が成立するか再検討が必要。ソフト担当・ハブとすり合わせ待ち。
11. **★の見た目**: NeoPixel発光のみで、実物のKTANEらしい質感(星形の光)が失われる可能性がある。簡易な見た目対策の要否をユーザーと相談。
